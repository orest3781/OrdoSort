# Highlighted-row text contrast — design

**Date:** 2026-08-02
**Status:** Fix for a measured defect ("fix all", user-directed)

## Context

Measured 2026-08-02 by off-screen harness (pixel scan + live DP read, both
themes) and confirmed by eye on rendered PNGs: the highlighted/selected row of
**every ComboBox drop-down** shows its label at **1.35:1 (light) / 1.27:1
(dark)** — AA requires 4.5:1. The `Bd` bar correctly flips to `Theme.Accent`
and `ComboBoxItem.Foreground` correctly flips to `Theme.AccentText`; the label
does not follow.

**Root cause.** The label is a `TextBlock` — either auto-generated by WPF
wrapping string `Content`, or written bare in a `DataTemplate`. The app's
implicit `TextBlock` style (`Theme/Styles.xaml:30-32`) sets
`Foreground = Theme.Text`, and **a style setter outranks an inherited value**,
so the trigger's `Foreground` never reaches the glyphs. This is the same
mechanism that made PrimaryButton labels near-invisible during the UI/UX
refresh; the note from that fix records that a `Style.Resources` remedy was
**proven non-functional** there, so the remedy here must be measured, not
assumed.

**Why the suite is green.** `ThemeTests.TextPairs()` asserts the *palette pair*
`AccentText` on `Accent` (which passes comfortably). It never asserts what a
rendered container actually resolves, so this class of defect passes CI
unseen.

## Scope — every container whose trigger flips `Foreground`

Static sweep of `Theme/Styles.xaml`, to be confirmed by measurement:

| Container | Trigger | Content element | Expectation |
|---|---|---|---|
| `ComboBoxItem` (:527) | `IsHighlighted` → AccentText | auto-wrapped `TextBlock`, and bare `TextBlock` in `KvpValueTemplate` / font picker | **broken — measured** |
| `DataGridCell` (:747) | `IsSelected` → AccentText | `DataGridTextColumn` generates `TextBlock` | **expected broken** — History, Bulk rename, Match & merge grids |
| `MenuItem` submenu (:385) | `IsHighlighted` → AccentText | header is `ContentPresenter ContentSource="Header"` → **`AccessText`**, not `TextBlock` | expected FINE (matches the 11.48:1 / 12.89:1 already measured) — but the template's explicit `Gesture` `TextBlock` (:398) must be checked |
| `TabItem` (:693) | `IsSelected` sets background/border/weight, **not** Foreground | — | not affected |

Every row above is **verified by measurement before and after** the fix; the
table's expectations are hypotheses, not conclusions.

## Remedy

One shared, surgical remedy applied to each broken template, chosen by
harness comparison rather than assumption. Candidate order:

1. **`ControlTemplate.Resources` implicit `TextBlock` style** in the affected
   template, `BasedOn` the app style, with
   `Foreground = {Binding Foreground, RelativeSource={RelativeSource AncestorType=<container>}}`.
   A style in a nearer resource scope wins over the app-level implicit style,
   and it reaches DataTemplate-generated TextBlocks too because resource
   lookup walks up the tree — a single point covering both item shapes. Note
   this is *not* the `Style.Resources` shape that failed before, but the
   difference must be proven, not argued.
2. **Fallback if (1) fails:** explicit content element with a *local*
   `Foreground` (local values outrank style setters) — the pattern that did
   work for the button labels.

**Considered and rejected:** deleting the `Foreground` setter from the
implicit `TextBlock` style and letting Foreground inherit from a Window-level
setter. Architecturally the cleanest — it removes the override that breaks
inheritance app-wide — but it changes the resolved colour of every bare
`TextBlock` on every screen, which is far too wide a blast radius for a
contrast fix. Recorded here so the option is not silently forgotten.

## Regression test (closes the CI gap)

Add to the WPF suite a headless test that asserts what a container *resolves*,
not what the palette contains: build the container with the app's resource
dictionaries applied, `ApplyTemplate` + measure/arrange, force the trigger
state, walk the visual tree to the actual text element, read its **effective**
`Foreground`, and assert `ContrastRatio(fg, bar background) >= 4.5` — in both
palettes, for each container fixed. A `[Theory]` over the container types
keeps it one test body.

This test must **fail before the fix and pass after** — demonstrated, not
claimed.

## Non-goals

- Restyling highlight colours, or changing which palette roles are used.
- Touching `TabItem` (its trigger does not flip Foreground).
- The app-wide implicit-`TextBlock`-style removal described above.
