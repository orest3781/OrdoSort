## Experiments — four standing [U]s, settled on this machine

All on local NTFS fixed volumes (C: → S:), .NET 8. **SMB behaviour remains untested** —
that caveat applies to every line below.

1. **Kill mid-copy across volumes (DW-01) — PROVEN, and worse than recorded.** A 2.5 GB
   `File.Move` C:→S: killed at ~150 ms left the destination at **full length**
   (2,684,354,560 bytes) with **incomplete data** — an end-of-file marker written into the
   source was absent from the destination's tail. CopyFile preallocates, so the partial
   file under the canonical name is *indistinguishable by size* from a complete one.
   Killed at ~350 ms (after copy, before delete): **both** a complete destination copy and
   the intact source remain. 08-04 §1.4 said "partial file"; the truth is "full-length
   corrupt file", which nothing downstream can even size-check.
2. **Read-only source, cross-volume (QC-03's cited trigger) — did not reproduce.**
   `File.Move` of a read-only file C:→S: succeeded and deleted the source. Same-volume
   control: also clean.
3. **Source held open without `FILE_SHARE_DELETE` (the AV/peer-preview trigger) — did not
   reproduce the silent branch.** `File.Move` threw `IOException`; source intact; **no
   destination copy left behind**. On local volumes .NET 8 fails loudly. The batch-A
   post-move guard remains justified — the documented MoveFileEx branch is now an
   SMB-only hypothesis.
4. **`KeyGesture` numeric key (QC-23) — CONFIRMED exactly as hypothesised.**
   `Enum.TryParse<Key>("300")` returns true with an undefined value;
   `new KeyGesture((Key)300, Ctrl)` throws `InvalidEnumArgumentException` — an
   `ArgumentException`, which `catch (NotSupportedException)` misses. QC-23's [U] is
   settled; only the fix remains.
5. **Trailing-space device names (DW-19) — downgraded.** `CON .pdf` and `PRN .pdf` create
   ordinary files on Win11 NTFS; no device capture, no error. Residual risk is older
   Windows / other stations only.

## High

### Q2-01 · Bulk Rename: after (or during) a batch, the button re-arms over the executed plans, and one click destroys the undo record
`BulkRenameViewModel.cs:157`, `:576-580`, `:592`, `:605-627` · `DebouncedProbe.cs:87-96` · **[V]** — found independently by two sweeps

The batch's `finally` clears the op fields, calls `Refresh(immediate: true)`, then
`IsBusy = false` under the comment "the tool only becomes usable again once its list
agrees with the disk." The comment is false: `Refresh` only *arms* the probe — the
re-plan (a `File.Exists` per file against the share) runs off-thread and `ApplyPlans`
lands later by a `Post`. Until it lands, `_changed` and `_lastRenderedPlans` are still
the pre-batch values, so the button re-enables reading "Rename 200 files" over a grid
showing plans that just executed. A second click enters `ApplyAsync`, and `:580` assigns
`_lastOutcomes = renamed` — a fresh empty list — **before the first move**. Every plan
then fails (sources renamed away), Undo goes permanently grey, and 200 real renames are
unrecoverable through the app. **Second trigger, same line:** a batch cancelled before
its first file (the natural "wrong rule, stop" reflex, or `Dispose` on close) also
replaces the *previous* batch's outcomes with the empty list — undo dies silently under
"Cancelled — renamed 0 of 12." Both vectors were created by `34ff78d`+`81e2c17`; the
early publish is the durability fix doing exactly what it was told, one caller wider
than intended.

### Q2-02 · MatchMerge runs `BulkRename.Execute`/`Revert` on the UI thread and records outcomes after the loop — QC-04, unpropagated
`MatchMergeViewModel.cs:82-83`, `:493`, `:505-511`, `:522-541` · `RelayCommand.cs:20` · **[V]**

`MergeCommand`/`UndoCommand` are plain synchronous `RelayCommand`s. "Merge 300 matched"
runs a `foreach` of `File.Exists`/`File.Move` against the share on the dispatcher — the
window freezes, Not Responding, no progress, no cancel — and `_outcomes`, the only thing
"Undo last merge" reads, is assigned in `Absorb` **after** `Execute` returns. Kill the

severity rationale, and the exact fix-template (its sibling's own `ApplyAsync`) as QC-04.
The VM even holds an `IWorkScheduler` it uses only for a roster `File.Exists`.

## What this method would miss

The same three honest limits as the last pass, narrowed: the experiments covered local
NTFS only — **every SMB-dependent [U] (QC-03's silent branch, Q2-04's trigger, R2's torn
copy, the stall durations) is still documentation, not observation**. Nothing here was
observed under two stations, a real printer queue, or a genuinely dead share. And a pass
aimed at the previous pass's blind spots inherits new ones of its own: nobody has yet
traced the XAML resource/binding layer (converters, styles, triggers) with the same
discipline, and the e2e suite's 38 scenarios haven't been asked the DW-77 question
("what did this actually demonstrate?") that the unit coverage suites just were.
