## The theme: a fix that landed in one place and not its sibling

This pass did not mostly find novel mistakes. It found **six** cases where a hazard was
correctly understood, correctly fixed, and documented in a comment — in one location,
while its structural twin was left alone.

| Fixed, with a comment explaining why | Never propagated |
|---|---|
| `Intake.Expand` got `EnumerationOptions{IgnoreInaccessible}` + a 12-line comment | `FolderMonitor.Status` still uses the aborting overload — **QC-01** |
| `FilenameList` got selection-restore yesterday (FL-03) | `BulkRename` drops selection identically — **QC-11** |
| BulkRename's *preview* moved off-thread, "must never run on the UI thread" | BulkRename's *actual renames* are on the UI thread — **QC-04** |
| Unlock's `Clear` carefully cancels the **probe** token, with a 4-line comment | It never cancels the **run** token — **QC-05** |
| `MatchMergeViewModel.Tokenize` splits on any Unicode whitespace, deliberately | `MatchMerge.Norm` splits on ASCII space only — **QC-16** |
| The filename-list design spec chose nullable `Size`/`Modified` "rather than lying with a 1601 date" | `Scanner.DeferredSummary` still lies with 1601 — **QC-13** |

That is the actionable insight: the fixes are mechanical, because the correct version of
each already exists in the repo, one file over, with its reasoning attached.

**QC-02 is the exception and worth reading separately** — there, every individual function
does exactly what its comment says, and the *composition* is wrong.

## High

### QC-01 · One unreadable subfolder blanks an entire watch tile
`FolderMonitor.cs:60-61` · vs `Intake.cs:33-49` · **[V]**

`Status` walks a recursive watch folder with the bare `SearchOption.AllDirectories`
overload. `Intake.cs:33-49` carries a comment explaining, in this codebase, why that is
wrong: *"The SearchOption overload aborts the WHOLE walk with UnauthorizedAccessException
at the first subfolder it can't open (denied ACL, cloud placeholder, junction) — losing
every file already found, not just the unreadable subtree."* `Intake.Expand` was fixed with
`EnumerationOptions { IgnoreInaccessible = true, AttributesToSkip = 0 }`. `FolderMonitor`
was not.

**Failure.** A recursive watch folder contains one subfolder the account can't read — a
locked-down archive, an unhydrated OneDrive placeholder, a junction. The walk throws at
that subfolder, wherever in the tree it sits. The catch at `:79-82` returns
`Count = 0, Matches = [], Error = "can't read folder: …"` for the **whole tree**. A file
named `URGENT` sitting in a fully readable sibling folder raises no alert. The tile shows a
permissions error, and nothing indicates a real match is hidden behind it.

**Fix:** the same `EnumerationOptions` in `FolderMonitor.Status`.

### QC-02 · A blank set-aside folder files patient documents into the config directory
`Config.cs:99` · `Config.cs:300-303` · `Session.cs:146` · `Commit.cs:84-86` ·
`SettingsViewModel.cs:2238-2240` · **[V]**

Every hop verified by hand:

- `Config.Deferred` defaults to `""`, and Settings never forces a value.
- `Warnings()` reads `if (deferred.Length > 0 && !_directoryExists(...))` — a **blank**
  set-aside produces **no warning at all**. Two lines above, a blank *inbox* does warn
  ("No inbox folder is set"). Two adjacent fields, opposite treatment of blank.
- `Config.ResolveBeside(cfgPath, "")` → `Path.IsPathRooted("")` is false →
  `Path.Combine(dir, "")` returns `dir`. **The blank becomes the config directory.**
- `Commit.SkipFile`'s guard is `IsNullOrWhiteSpace(deferredDir) || !Directory.Exists(...)`.
  `deferredDir` is now the config folder: not blank, and it exists. **The guard cannot
  fire, and its `"(not set)"` branch is unreachable from the shipped app.**

**Failure.** Fresh install. The user sets an inbox and three routes, never touches the
set-aside field, gets no warning. They press Space on a document. It moves next to
`config.json`, `destinations.json`, `history.sqlite`. The UI says *"✓ Set aside for later"*.
Patient documents accumulate permanently in the app's config folder — a location no screen
presents as a document location.

**Knock-on, verified:** `Scanner.DeferredSummary` (`Scanner.cs:83`) uses
`Directory.GetFiles` with **no extension filter**, so a fresh install shows
*"N set-aside files waiting"* counting `config.json`, `names.txt`, `history.sqlite`.

**Test gap, verified:** `SessionDeferredResolutionTests` has exactly two tests, both with a
non-empty deferred value. Nothing anywhere passes a blank one.

**Why it survived four audits:** each function does exactly what its comment says.
`ResolveBeside` correctly resolves a relative path. `SkipFile` correctly guards a blank
folder. `Warnings()` correctly declines to nag about an optional field. Only the
composition is wrong. It was found by asking *"what does an empty string do at each hop"*,
not by reading any one function.

### QC-03 · A cross-volume `File.Move` can report success and leave the original in place
`Commit.cs:28-41` · `Commit.cs:145` · **[V]** on the code · **[U]** on the Win32 branch

`MoveNeverOverwrite` treats a non-throwing `File.Move` as proof the document moved.
Grepped: the only `File.Exists(src)` calls in `Commit.cs` are the *pre*-checks at `:46` and
`:82`. **Nothing re-checks the source after the move, anywhere in `Commit.cs` or
`Session.cs`.**

.NET's `File.Move` is `MoveFileExW` with `MOVEFILE_COPY_ALLOWED`, documented as: *"If the
file is successfully copied to a different volume and the original file is unable to be
deleted, the function succeeds leaving the source file intact."* Inbox on one share and
routes on another is the normal deployment.

**Failure.** A read-only source (this repo ships `docs/RemoveReadOnly.ps1`, a bulk
read-only stripper, so these demonstrably occur here), or any holder without
`FILE_SHARE_DELETE` — a peer's preview, an AV scanner. Copy succeeds, delete fails,
`MoveFileEx` returns TRUE, no exception. UI: *"✓ Filed"*. A history row is written. `Pos++`.
The original is still in the inbox. **Undo then refuses** — `Commit.cs:145`'s
`if (File.Exists(originalPath))` guard fires — so the user has two copies under two names
and no way back through the app. QC-12 is what stops it ever being re-offered.

**Fix:** one stat. After `File.Move` returns, `if (File.Exists(src)) throw new CommitError(…)`.

### QC-04 · Bulk Rename performs the renames on the UI thread, and a force-kill loses undo
`BulkRenameViewModel.cs:135-136`, `:354-379` · `Mvvm/RelayCommand.cs:20` · **[V]**

`RenameCommand`/`UndoCommand` are plain `RelayCommand`, whose `Execute` is
`=> _execute()` — synchronous. `Apply()` calls `BulkRename.Execute`, a `foreach` of
`File.Exists`/`File.Move`. The view model's **only** scheduler use is `_plansProbe`, the
*preview*. Its own class comment says the preview must be off-thread because
`File.Exists` on an SMB destination is too expensive for the UI thread.

Every sibling tool — ZipTools `RunBatchAsync`, PageCounts, Unlock — runs its file work
through `Scheduler.Run` with a live "N of M" status.

**Failure.** 200 files from a share, click Rename. WPF is single-threaded: the whole app
freezes and Windows marks it Not Responding, with no progress and no cancel. Worse:
`_lastOutcomes` — the only thing Undo reads — is assigned **after** the loop completes. A
user who force-kills an app they believe is hung is left with files renamed on disk and no
undo path.

### QC-05 · *Clear* and *Remove selected* don't cancel an in-flight batch
`ZipListViewModel.cs:111-117`, `:179-183`, `:271` · `UnlockViewModel.cs:232-246` · **[V]**

`ZipListViewModel.Cancel()` is called from exactly one place in the app:
`ZipToolsWindow.xaml.cs:68`, the `OnClosed` handler. Neither `ClearCommand` nor
`RemoveSelected` touches `_cts`. `RunBatchAsync` snapshots `pending` before the loop;
Unlock's `UnlockAsync` snapshots `rows`. Neither Clear nor Remove is gated on a busy flag.

**Failure (Unlock — it moves real files).** Drop 5 PDFs, click Unlock, then select the 3rd
row and click *Remove selected* to pull it out of the batch. It vanishes from the list, and
the running loop still processes it: the locked original is archived and the unlocked file
written. When the run ends, a result line appears for a file the list no longer shows. Click
*Clear* instead and `Summary`/`ResultLines` wipe, then silently repopulate seconds later
with results for files the user just cleared.

**The telling detail:** Unlock's `ClearCommand` carries a four-line comment reasoning
carefully about cancelling the **probe** token so a stale probe can't update an invisible
row. The same author, in the same method, never cancels the **run**.

### QC-06 · An unparseable label number is silently written to disk as 1
`LabelMakerViewModel.cs:50-51`, `:555`, `:671` · `LabelMakerWindow.xaml.cs:19` · **[V]**

```csharp
DestroyDays = int.TryParse(DestroyDaysText.Trim(), out var d) ? d : 30,
NextNumber  = long.TryParse(NextNumberText.Trim(), out var n) ? n : 1,
```

A silent fallback, not a refusal. `Persist()` runs from `Closing` on **every** close

**Failure.** A client sits at 4211. The user clicks into the number box and either clears it
intending to retype, or types `4,211` — `long.TryParse` with default `NumberStyles.Integer`

box number as the exact outcome the placement rules exist to prevent.

Same shape silently rewrites retention to 30 days, printing destruction dates years early.
Tests exercise `Persist` with valid values only.

### QC-07 · The duplicate-id refusal cannot stop the close, and its wording says otherwise
`LabelMakerViewModel.cs:593-602` · `LabelMakerWindow.xaml.cs:19` · **[V]**

```csharp
Closing += (_, _) => vm.Persist();     // CancelEventArgs discarded; Persist returns void
```

`Persist` warns *"Two clients share the id … fix the duplicate before closing; nothing was
saved."* and returns. The window closes anyway, and because the guard returns before
`BoxLabelStore.Mutate` is entered, **every edit in the session is discarded** — including
deliberate counter corrections on unrelated clients. The message instructs the user to do
something they can no longer do.

**Fix:** `Persist` must report refusal, and the handler must set `e.Cancel = true`.

### QC-08 · Two side-file keys pointing at one file silently destroy the first written
`Config.cs:492-497`, `:617-621` · `SettingsWindow.xaml:1566,1585,1604` ·
`SettingsViewModel.cs:1189-1215` · **[V]**

`Save` writes destinations → monitored-folders → alerts in sequence, and `WriteDoc` →
`WriteJson` → `WriteAtomic` is a **full re-serialization of one doc type**, not a
read-modify-write. Grepped: **no uniqueness check across the four keys exists anywhere** —
only `??=` defaults and per-path confinement.

**Failure.** Point `monitored_folders_file` at `destinations.json`. `Save` writes
`{"routes":[…]}`, then overwrites the same file with `{"watch_folders":[…]}`. `TrySave`
returns `ok = true` — both writes genuinely succeeded as I/O. On next load `cfg.Routes` is
`[]`. Every filing destination is gone, with nothing in the UI, the return value, or the
JSON to say so.

Reachable from the shipped app: all four are free-text boxes with Browse buttons, and
`PickSideFile` validates **confinement only**.

**Root cause is architectural.** Each field owns an independent `DebouncedProbe` note
(`SettingsViewModel.cs:617-627`) that sees only its own value. A collision is the one
constraint that lives *between* fields, and the per-field design has nowhere to put it —
which is why a per-field validation pass could not have caught it.

### QC-09 · Nine overflow-probe cases examine zero elements — proven by mutation
`tests/OrdoSort.Wpf.Tests/OverflowProbe.cs:51` · `WindowOverflowTests.cs:326, 368, 418, 449`
· **[V] — settled empirically, not by reading**

`OverflowProbe.Escapees` skips every candidate with
`if (!e.IsVisible || e.ActualWidth == 0) continue;`. Four call sites `Measure`/`Arrange` a
bare view that is never hosted in a shown `Window`, so every candidate is skipped and
`Assert.True(offenders.Count == 0, …)` is unconditionally green.

**Settled by mutation rather than argument.** With `MinWidth="2000"` injected into a
`TextBlock` in `DoneView.xaml` — a 2000px element inside a 370px panel, exactly the defect
the probe exists to catch — a full rebuild and a filtered run gave:

```
Passed!  -  Failed: 0, Passed: 7, Skipped: 0, Total: 7
```

`DoneViewFitsTheParkedPanel` passed with the injected overflow present. The file was
restored from backup and `git status` confirmed clean.

Affected: `ProcessingViewFitsTheParkedPanel` (2 cases), `ReadyViewTilesFitThePanel` (3),
`DoneViewFitsTheParkedPanel` (2 — **proven**), and the `probe.Show == false` branch reached
only by the **TriageWindow** entry (2) — the widest window in the app, which the class doc
at `WindowOverflowTests.cs:45-47` presents as covered. `LabelMakerOverflowTests` and the
main `NoTextElementEscapesTheWindow` path both call `window.Show()` and are unaffected.

This is the failure the class's own doc warns about at `:36-37` ("an empty window trivially
fits"), arriving through a different door.

**Fix:** floor the probe — return the examined count and `Assert.True(examined >= 5)` — or
host the view in an off-screen `Window` that is actually `Show()`n, as

## What this method would miss

Nine static sweeps plus one green dynamic baseline. Three honest limits.

**Static reads confirm that code does what it says; they are weakest exactly where a
composition of individually-correct functions is wrong.** QC-02 is the proof — every hop has a
comment, every comment is accurate, and the result is a patient document in the config folder.
It was found by tracing one value (`""`) through every hop, and the hops nobody thought to
trace that way are the ones still hiding. The 2026-08-07 sweep wrote down this same lesson
after missing D5; it is still the sharpest edge here.

**Everything that turns on Win32 or BCL behaviour under failure is reasoned from
documentation, not executed** — QC-03's `MoveFileEx` branch, QC-23's `KeyGesture` exception
type, QC-25's `SemaphoreSlim.Dispose` semantics, the trailing-space device-name case. Each is a
five-minute experiment, and QC-03 is the one worth doing first, because documentation being
wrong is precisely what would let a defect of that shape survive four prior audits.

**Nothing here was observed under two stations on one share, a genuinely slow SMB path, a real
printer, or a dead WebView2 process** — which is where QC-15, QC-18, QC-19, QC-27 and QC-28
live. The green e2e run is real evidence for the 38 scenarios it covers, and QC-09 is a
reminder that a green assertion is only evidence once you know it examined something. The same
question — *what did this actually measure?* — has not been asked of the other coverage-style
suites in this repo, only of the two named in QC-09 and QC-26.
