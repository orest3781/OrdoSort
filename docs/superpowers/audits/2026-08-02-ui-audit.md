## Important

### Keyboard & accessibility

- **I1 — Unlock: Enter does nothing.** `UnlockWindow.xaml:12-24`. The primary
  Unlock button has no `IsDefault` and the password box has no Return
  `KeyBinding`. You type a password and press Enter and nothing happens, with no
  alternate gesture. In a keyboard-first app this is the sharpest edge found.
- **I2 — Settings hotkey capture swallows Escape.** `SettingsWindow.xaml.cs:27-57`
  (bound at `SettingsWindow.xaml:452-454`) sets `e.Handled = true`
  unconditionally (Tab exempted), so pressing Esc while focus is in the
  hotkey-capture box assigns the hotkey "Escape" instead of closing the dialog.
- **I3 — Focus ring covers only buttons.** `Theme/Styles.xaml:48,99` assigns the
  shared `BronzeFocusVisual` to Button and ToggleButton only. CheckBox,
  RadioButton, ComboBox, ListBoxItem and TabItem fall back to the stock OS
  dashed rectangle — the one place the theme's focus language breaks.

### Copy & information

- **I4 — "Route" vs "Destination".** `HistoryWindow.xaml:45` labels a column
  "Route" while Settings, its buttons and its validation text all say
  "Destination(s)" — and `RouteButtonViewModel.cs:9-11` documents them as
  "destination buttons". One user-facing word should win; "Route" is the
  internal name.
- **I5 — "Dashboard" vs "Monitored folders".** `SettingsWindow.xaml:563` titles
  the tab "Dashboard" while its own section header (`:571`) and the Data-files
  field (`:1211`) call the same feature "Monitored folders".
- **I6 — The catch-all error says "Something went wrong".**
  `ShellViewModel.cs:96-98` and `App.xaml.cs:20-22` open with that phrase and
  then dump raw exception text. Everywhere else this app explains consequences
  plainly; this is the one place it doesn't.
- **I7 — History has no empty state and no `TextTrimming`.**
  `HistoryWindow.xaml:26-48`. An empty log renders as a blank void (only the
  "0 of 0 filings shown" footer hints), and its fixed-width Name/Route columns
  clip without ellipsis — unlike BulkRename/MatchMerge, which deliberately use
  `Width="*"` for equivalent text.

### Visual consistency

- **I8 — Box labels has two competing primary actions.**
  `LabelMakerWindow.xaml:11` vs `:20`: "Print…" is styled `PrimaryButton` while
  the equally weighted "Save PDF…" is left default. Every other multi-action
  window has exactly one primary.
- **I9 — `FontSize="11"` hand-written ~20 times** instead of the existing
  `CaptionText` style (`MatchMergeWindow.xaml:44,102,108`;
  `LabelMakerWindow.xaml:81,143,158,212`; `SettingsWindow.xaml:348,814,882,890,1163`;
  others). Several sites reassemble it as `Style="SubtleText" FontSize="11"`,
  i.e. bypassing the type system rather than extending it.
- **I10 — The `FieldRow`/`FieldLabel` pattern is trapped in SettingsWindow**
  (`SettingsWindow.xaml:15-21`), so BulkRename, LabelMaker, MatchMerge and
  Unlock each hand-roll the same "label: value [Browse…]" row with different
  column widths and margins. This is where drift originates.
- **I11 — The documented spacing rhythm is wrong.** `8` appears 80 times as a
  margin/padding component — more often than `10` (62). The practiced rhythm is
  6/8/10/16; the theme file documents 6/10/16. Reconcile in one direction.

## Minor (selected — full lists in the pass reports)

- **M1** Ready screen's set-aside banner wraps mid-phrase ("… — click to /
  open") at the dashboard's natural width.
- **M2** Settings' General tab is ~55% empty because the window is sized for the
  tallest tab; it is the first tab a user sees.
- **M3** Settings' informational notes ("relative — resolved beside the config
  file") use the amber status colour, which elsewhere means *needs attention*.
  Prefer `SubtleText` and reserve amber.
- **M4** "Start Processing" (`ReadyView.xaml:145,149`) is the only Title-Case
  button in an app that is sentence case everywhere else.
- **M5** Settings' six tab headers carry no access-key mnemonics, though both
  tab templates already set `RecognizesAccessKey="True"`.
- **M6** The four ↑/↓ reorder buttons (`SettingsWindow.xaml:290-293,584-587`)
  have tooltips but no `AutomationProperties.Name` — screen readers get a bare
  glyph.
- **M7** The Appearance tab's theme-preview cards use ~22 literal hex colours
  (`SettingsWindow.xaml:997-1051`). Necessary — they show both palettes at once —
  but hand-picked independently of `ThemePalette.cs`, so they can silently drift
  from the real palette. Worth binding, or a test.
- **M8** Bulk rename's fifth "delete segment" checkbox renders with no visible
  label despite `Content="last"` (`BulkRenameWindow.xaml:78`) — verify whether
  render artifact or a new instance of the auto-wrap foreground trap.
- **M9** Triage shows *both* candidate rows in the selected treatment
  (`Triage-dark.png`), which `SelectionMode="Single"` should make impossible —
  verify whether demo state or an alternating-row resolution bug.
- **M10** *(was C1, Critical — downgraded 2026-08-02; see the correction note
  under "Critical" above)* — **History and Bulk rename's star columns
  collapse in headless capture, not on-screen.**

  **CONFIRMED by measurement**, not inferred from a screenshot.

  `HistoryWindow.xaml:42-43` (`Original`, `Filed as`) and
  `BulkRenameWindow.xaml:125-142` (`Current name`, `New name`) were `Width="*"`
  with no explicit `MinWidth`. Measured `ActualWidth` after a real `Show()` at
  declared size, with zero rows AND with five populated rows:

  | Window | Column widths measured |
  |---|---|
  | History (grid 936px) | When 140 · **Original 20** · **Filed as 20** · Name 160 · Route 120 · Undone 70 — 406px unused |
  | Bulk rename (grid 776px) | **Current name 20** · **New name 20** · Note 220 |

  Both star columns pinned to WPF's default `MinWidth` of 20 instead of their
  fair share (~222px and ~277px respectively). Every ancestor from the
  DataGrid up to the Window reported the correct `ActualWidth` with
  `HorizontalAlignment=Stretch`, so this was **not** an ancestor-sizing
  problem.

  **Cause:** WPF's DataGrid star-width computation does not resolve on the
  first Measure/Arrange pass produced by a `Show()` that is off-screen and
  never subsequently resized/activated — exactly the shape this project's own
  `Screenshots.cs` QA gallery tool uses to capture every window. Eight further
  pumped `UpdateLayout()` passes left the columns frozen at exactly 20px, while
  a ±1px width nudge (one genuine `SizeChanged`) immediately snapped them to
  222px / 277px. `HorizontalScrollBarVisibility` and
  `EnableColumnVirtualization` were ruled out.

  **ON-SCREEN CONFIRMATION (2026-08-02) — what downgraded this finding:**
  launched the real, interactively-shown app and drove it with UI Automation
  (real menu clicks), capturing the real HWND with `PrintWindow`. Both windows
  resolve their star columns to genuine fair share (~222px/~277px, matching
  the hand-computed numbers above), confirmed with 0 rows and with 5 populated
  rows. **A real user never sees the 20px collapse.** It is confined to
  headless/off-screen rendering. This audit's own gallery captures
  (`History-dark.png`/`History-light.png`, `BulkRename-dark.png`/
  `BulkRename-light.png`, referenced by the rendered-gallery pass this audit
  drew on) were themselves misleading as a result — they show the collapse,
  which no user ever experienced.

  **Impact (corrected):** none for real users at the default window size — not
  the "defeats the History window's purpose" impact originally claimed. The
  practical impact is that this project's own QA screenshot gallery
  misrepresented these two windows: a fidelity problem for the audit/QA
  process, not a defect the windows themselves have for a user. (A follow-up
  measurement also found the shipped fix genuinely protects a real user who
  shrinks the History window to its own declared minimum width, 700px — see
  the Task 1 report — so it was not purely a tooling accommodation either.)

  **Fixed:** explicit `MinWidth="120"` added to all four star columns (Task 1,
  2026-08-02) — full writeup, including the negative results from three other
  attempted fixes, in
  `.superpowers/sdd/2026-08-02-audit-remediation/task-1-report.md`.

## What holds up

Worth stating plainly, because an audit that only lists faults misrepresents
the codebase:

- **Theming is genuinely complete.** Every window's chrome, tabs, inputs,
  buttons, menus, scrollbars and tooltips are themed in both palettes. Zero
  accidental hardcoded colours outside the deliberate preview cards. The only
  stock chrome left is the two documented, independently verified
  DocumentViewer residuals.
- **Keyboard model is strong.** Global filing hotkeys (Ctrl+K, Ctrl+Shift+Z,
  Esc, Ctrl+, and route Ctrl+1–9) work window-wide and are validated live
  against duplicate *and* reserved-gesture collisions
  (`SettingsViewModel.cs:612-651`). MainWindow's menu mnemonics are complete and
  collision-free. Triage's focus-independent keyboard model is a standout.
- **Copy is unusually careful** in the filing loop: last-action cards,
  audit-failure messages and Settings' live validation all explain consequences.
  The ellipsis-on-dialog-opener and trailing-colon conventions are applied with
  **zero violations found app-wide**. Empty states elsewhere echo their own
  button's label.
- **Every dialog declares `MinWidth`/`MinHeight`.**
- Consistent 4px corner language, disciplined 0/1 border thickness, coherent
  PrimaryButton/ChipButton usage, and a Styles.xaml documented well enough that
  auditing it was straightforward.
