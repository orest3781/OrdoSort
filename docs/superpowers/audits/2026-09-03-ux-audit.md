# UX audit — every surface against the laws of UX

**Date:** 2026-09-03 · **Tree:** `main` @ `8e77436` (v1.5.4 plus one test fix)
**Scope:** all 21 XAML surfaces and their view models — the routing loop (Ready →
Processing → Done), MainWindow, Settings (seven tabs), History, the ten tool
windows, and the dialogs.

**Lens.** This is not a defect hunt (that was `2026-08-21-app-qc.md` and
`2026-08-22-fresh-qc.md`) and not a chrome/contrast/overflow pass (that was
`2026-08-22-ui-full-audit.md`). It asks one question per screen — *what is the one
thing the user came here to do, and does the screen make it unmistakable, fast,
forgiving, and well-ended?* — and scores the answer against the cognitive laws that
predict where users fail, as catalogued in the `ux-design` skill's reference: Fitts,
Hick, Jakob, Miller, Parkinson · Proximity, Similarity, Common Region, Prägnanz,
Uniform Connectedness · Aesthetic-Usability, Peak-End, Serial Position, Von Restorff,
Zeigarnik, Goal-Gradient · Doherty, Occam, Pareto, Postel, Tesler. One law per
finding; a finding with no law is taste and was left out.

**Method.** Six read-only sweeps, one per surface group (routing loop · Settings ·
rename/list tools · PDF/zip tools · naming/labels/History/dialogs · cross-cutting
consistency). Each was required to cite `file:line`, to cite the view-model line
behind any enablement or feedback claim, to grep the refinement checklist and the
08-22 audit before reporting, and never to reason about pixel layout from XAML —
the 08-22 live pass overturned three findings of that shape. Every Critical and
Major was then re-read in source by the controlling session, which corrected four
sweep claims (*Sweep corrections*). **A same-day QC pass** by five further read-only
agents that had not written the audit then re-opened every citation, hunted for
misses, and de-duplicated against the tracker; it confirmed all 32 original findings,
corrected eleven details, narrowed one, and added six (*QC pass*, at the end).

**No live pass was run.** Every finding here is a code path or a missing control,
not a measured layout, so each carries **[V]** (traced to source, citation given).
The two whose *consequence* deserves a running-app confirmation (UX-02, UX-34) also
carry **[U]** with the exact thing to measure.

**38 findings — 2 Critical · 17 Major · 19 Minor.** Numbered `UX-01`…`UX-38`; the
IDs are stable, so UX-15 keeps its number although the QC pass moved it to Minor,
and UX-33…38 are the QC additions. Tiers are the UX-audit ladder (Critical blocks
the task or yields a wrong result · Major is measurable friction · Minor is polish);
on the house ladder read Critical as High, Major as Important. Ranked within a tier
by user impact, never by fix cost. Nothing was fixed in the pass that produced this
file.

**Status 2026-09-05: batch 1 FIXED.** The fifteen findings of *Recommended order*
batch 1 — UX-01, UX-02, UX-03, UX-07, UX-06, UX-05, UX-19, UX-22, UX-20, UX-31, UX-32,
UX-35, UX-37, UX-38, UX-36 — are fixed on branch `fix/ux-audit-2026-09-03`, one

## What is already solid

Stated first so the fixes below do not regress it. QC verified every bullet
against source; none was overstated.

- **The routing loop's feedback is proportional and inline.** A route-coloured
  confirmation card sits below the buttons and expires itself (4 s,
  `ShellViewModel.cs:1161`); a new arrival mid-session joins the queue with a note;
  Done says "N filed, M set aside" and claims "every move is in the log" only when
  that is true (`:1375-1379`); Undo from Done re-enters Processing rather than
  dead-ending.
- **Every question dialog defaults to the safe answer**, handles Esc once at window
  level, and uses verb labels (`MessageWindow.xaml.cs:71-81`). All six `Confirm`
  call sites guard something genuinely irreversible (a box-label counter, a peer
  station's edits, seven tabs of edits). No confirmation in the app should be an
  undo instead — a rare clean sheet.
- **Standardise names is the cleanest window in the app**: the drop is the action,
  every row shows before → after with the refusal reason inline, Undo is scoped to
  what actually reverted, and the date prompt defaults to the last date typed.
- **Match and merge explains itself**: the bucket line and count-bearing buttons
  mean a disabled *Review matches…* is never an unexplained grey button.
- **Empty states are designed, and tell "nothing here" from "nothing matches"** —
  History (`HistoryWindow.xaml:293-309`), Filename list (`:308-328`), Ready's calm
  empty inbox, Page counts' drop-zone copy.
- **Merge PDFs asks for the output location before the work**
  (`MergePdfsViewModel.cs:423-430`), ships the new file types switched off
  (`DocumentConverter.cs:58-70`), and reports a missing Office app at drop time.
- **Unlock's wrong-password loop is inline** (retry in place, "save it as…" offered
  right there); Zip promotes a typed password to the front for the rest of the run.
- **The WebView2 failure messages are the model for error copy**:
  `WebViewPdfViewer.cs:25-40` say what still works and what to install, and send the
  technical detail to `crash.log`. UX-33 is about the catch-all sites that do not
  follow them.
- **Keyboard focus is visibly distinct from hover** on every control, pixel-tested;
  the name box, the password box and the date prompt all take focus explicitly.
- **Every tool window opens the same way** — same title shape, owner, modality,
  MinWidth/MinHeight, no taskbar entry — and the Tools menu's four separator
  groups follow a real axis (rename · print · inventory · containers).

## Critical

### UX-01 — a failed filing wipes the name the user just typed (Processing) [V] — **FIXED 2026-09-05 (6278646)**
*Peak-End* (the flows reference: "Never lose data… Losing a user's typed data is the
single most reliable way to lose the user"). This is the highest-frequency screen in
the app and its worst-designed moment.

`LoadCurrentAsync` resets the box unconditionally — `ShellViewModel.cs:1360`
(`_typedName = "";`). `OnRouteAsync`'s `CommitError` catch warns and then calls it
anyway (`:1436-1437`, beside the comment "reload the same doc; nothing moved"), and
`OnSkipAsync`'s `CommitError` catch falls through to the same reload (`:1471-1477`).
`Session` advances only on success, so the same PDF comes back with an empty box
after the modal. Route buttons are enabled by *route* validity, not name validity
(`ProcessingView.xaml:81` `IsEnabled="{Binding Enabled}"`,
`RouteButtonViewModel.cs:48`), so an illegal name (`Naming.RejectIllegal`,
`Naming.cs:102`, rewrapped as `CommitError` at `Commit.cs:103`) or an unreachable
destination reaches this path with the name typed. No existing test asserts the
name survives a failed commit.

**Fix:** split `LoadCurrentAsync` into "new document" (clears) and "same document"
(refreshes metadata and preview, keeps `TypedName`), or guard the reset on the path
having changed. **Pin:** a `ShellViewModel` test where the commit throws
`CommitError` asserts `TypedName` and `CurrentFilename` are unchanged afterwards —
fails today.

### UX-02 — sorting Bulk rename's preview breaks "next file needing a name" [V][U] — **FIXED 2026-09-05 (183691f)**
*Zeigarnik* — the navigator exists to walk the user through the unfinished set, and
a sort sends it to the wrong row.

`BulkRenameWindow.xaml:177` declares `PreviewGrid` without
`CanUserSortColumns="False"` (the Filename list sets it at
`FilenameListWindow.xaml:132` — for a different reason, its "#" column), so any
header click sorts the view. `OnJumpToNextStray` (`BulkRenameWindow.xaml.cs:60-66`)
and the post-edit auto-advance in `OnCellEditEnding` (`:128-137`) read
`PreviewGrid.Items.IndexOf(row)` — **view order** — pass it to
`IndexOfNextNeedingName` (`BulkRenameViewModel.cs:457-465`), which walks `Preview`
in **insertion order**, then index `PreviewGrid.Items[next]` — view order again.
WPF sorts the view, never the source collection, so the two spaces agree only while
unsorted. After a sort, F2 / Enter / "next stray" opens an arbitrary row and
`BeginEdit` seeds it; in the type-Enter-type-Enter rhythm the comment at `:131-133`
designs for, a name can be committed onto a row that did not need one. Undo exists,
but only if the user noticed. The existing tests (`ToolViewModelTests.cs:1214-1261`)
exercise the walk against an unsorted collection only.

**[U] measure:** on a batch with strays, click the Result header, press Enter on a
stray, read which row opens. **Fix:** `CanUserSortColumns="False"` (one attribute)
— or navigate by `RenameRow.Source` identity. **Pin:** a WPF test that adds a
`SortDescription` to the grid, invokes the jump, and asserts the row in edit has
`NeedsName` — fails today.

## Major

### UX-03 — Enter in almost any Settings text box commits and closes all seven tabs [V] — **FIXED 2026-09-05 (009aea3)**
*Jakob* — Enter acts on the control in hand; the app's own alert-term box does
exactly that two lines away from this pattern.

OK is `IsDefault` (`SettingsWindow.xaml:156`). Only three text inputs intercept
Return — the hotkey box (`:656`), the section editor (`:995`), the alert-term box
(`:1334`). Every other `TextBox` (inbox `:241`, deferred, the four side-file paths,
route Label / Folder / Suffix / Colour, watch Label / Folder, separator, poll
seconds, font size) lets Return reach OK, which runs `TryBuildResult` across every
tab and closes on success (`SettingsWindow.xaml.cs:22-25`,
`SettingsViewModel.cs:2363-2403`). Mid-edit Enter therefore either pops a pooled
validation dialog about *other* tabs, or saves-and-closes with half-reviewed edits.

**Fix:** a shared `PreviewKeyDown` on the window's TextBoxes that swallows Return
(the UI-08 fix in `ManageSavedWindow`, inverted), or drop `IsDefault` from OK.
**Pin:** with focus in the Inbox box, Enter leaves the window open — fails today.

### UX-04 — an Office-document merge is one frozen status line, and the only way out is unlabelled (Merge PDFs) [V]

*Doherty* — anything past ~5 s needs real progress and a way to leave.

`MergePdfsViewModel.cs:467-473` puts every loose (non-zip) row into **one** unit.
`RunBatchAsync` writes `"Merging 1 of 1…"` once per unit (`ZipListViewModel.cs:596`)
and checks cancellation only *between* units (`:591-593`). Each document is a live
Word / Excel / PowerPoint round-trip (`OfficeConverter.cs:311-525`); eight Word
documents show one unchanging line until all eight have gone through Office.

QC correction: the view model does inherit cancellation — `ZipListViewModel.cs:282`
(`_cts`) and `Cancel()` (`:690-694`) — and `MergePdfsWindow.xaml.cs:119-124` fires
`Cancel()` on close, so Close (or Alt+F4) does leave, dropping queued units; the
code-behind's own comment (`:110-118`) records that a unit already mid-conversion
keeps running detached. What is missing is a *labelled* Cancel and any progress
finer than "1 of 1".

**Fix:** one unit per loose document — `RunBatchAsync`'s "n of N" then applies for
free and Cancel lands between documents — plus a Cancel button in the Unlock shape
wired to the `Cancel()` that already exists. **Pin:** three loose files through a
stub converter raise three distinct `Status` values — fails today.

### UX-05 — Print can freeze Box labels for five seconds with no busy state [V] — **FIXED 2026-09-05 (c6caf67)**
*Doherty*, on the window's single primary button.

`LabelMakerViewModel.Print` (`:478-495`) calls `ClaimNumbers` synchronously at
`:489`; the method's own comment says so (`:450-453`: "UI-thread only… SavePdfAsync
uses ClaimNumbersCore instead so the file work can run off-thread").
`BoxLabelStore.cs:12` retries a contended file for `DefaultMaxWaitMs = 5000`.
`PrintCommand` is a plain `RelayCommand` (`:233`), there is no `IsBusy` in the
class, and no disabled state — the button just stops answering. Q2-21 is the same
file lock in the constructor; DW-63 asked for this in `SavePdf`, which already has it.

**Fix:** make `Print` async through `_scheduler.Run(ClaimNumbersCore)` exactly as
`SavePdfAsync` (`:499-527`) already does two methods down; disable Print while the
claim is out. **Pin:** a store stub that blocks for a second does not block the
dispatcher — fails today.

### UX-06 — History shows a blank grid during a slow load, and Show all can run twice [V] — **FIXED 2026-09-05 (0d59b03, 523de1a)**
*Doherty* — keep the stale content or show the shape; never a blank region.

The class says the risk out loud (`HistoryViewModel.cs:38-42`: a query on a share
"takes seconds"). `LoadAsync` (`:106-122`) is off-thread — good — but the class has
no `IsBusy` at all; `Rows.Clear()` runs *after* the query and `IsEmpty` is only true
after load, so during the wait neither the grid nor the empty-state text shows.
`ShowAllCommand` is a plain `RelayCommand` gated on `!_showedAll` only (`:79`), and
`_showedAll` is set at the end of the load (`:116`): a second click during a slow
load starts a second `LoadAsync(all: true)`. (The reentrancy-safe `AsyncRelayCommand`
the app uses elsewhere would have prevented this.) Q2-28 is the same method's
missing exception handling — a different bug.

**Fix:** an `IsBusy` flag driving a "Loading…" row (or skeleton rows) and gating
Show all. **Pin:** `ShowAllCommand.CanExecute` is false while a load is in flight —
fails today.

### UX-07 — building a zip shows nothing until it is finished (Zip and unzip) [V] — **FIXED 2026-09-05 (7144633)**
*Doherty*. Sibling of **QC-31** (open), which records the same method from the
lifecycle side — `ZipAsync` ignores cancellation and `IsBusy`, so closing the window
mid-zip leaves it running. This is the feedback side; cite both.

`ZipAsync` (`ZipExtractViewModel.cs:88-97`) awaits `Scheduler.Run(_zipper…)` and
only then writes `Status`; it never sets `IsBusy`. Its sibling `ExtractAsync` goes
through `RunBatchAsync` (`ZipListViewModel.cs:586-596`), which sets `IsBusy` and
"Extracting n of N…" before each unit. Compressing a large folder is silent, with
every button still live.

**Fix:** route `ZipAsync` through `RunBatchAsync` as one unit (which also closes
QC-31), or at minimum `IsBusy = true` and `Status = "Zipping N items…"` around the
run. **Pin:** `Status` changes before the zipper stub completes — fails today.

### UX-08 — removing a saved password is instant, permanent, and looks like Add [V]

*Jakob* — every platform the user knows either confirms an irreversible delete or
offers an undo; the feedback reference's delete table says the same. Manage saved
passwords does neither.

`RemoveSelectedSaved` (`UnlockViewModel.cs:485-500`) removes the entry from the
config, persists it (`_trySaveCfg`) and re-probes — no `Confirm`, no undo, and the
password is recoverable from nowhere else. `ManageSavedWindow.xaml:59-62` gives Add
and Remove the same plain style, side by side.

**Fix:** "Removed 'label' · Undo" for a few seconds (cheapest, and the app's own
preferred shape), or a one-line confirm naming the label. Plus UX-10's style.
**Pin:** Remove then Undo restores the entry and re-persists (a forward pin for the
fix; nothing to assert today).

### UX-09 — removing a destination or monitored folder has no undo but Cancel-everything (Settings) [V]

*Occam* — inline undo beats a confirm dialog, and it certainly beats neither.

`RemoveRouteCommand` / `RemoveWatchCommand` (`SettingsViewModel.cs:707-709`,
`:737-739`) remove and `Dispose()` on click, no confirm, and there is no undo
anywhere in the class. In the XAML, Remove sits in the same plain style between
Duplicate and ↑ on the Destinations tab (`SettingsWindow.xaml:426-435`) and between
Add section and ↑ on the Monitored folders tab (`:848-856`). The only recovery for a
misclick is Cancel — which, since UI-06's fix, asks first, and then throws away
every other edit across seven tabs.

**Fix:** a local "Removed 'Legal' · Undo", or at minimum UX-10's destructive style
and a gap before Remove.

### UX-10 — there is no destructive button style, though the palette defines the tokens [V]

*Similarity* — the app trains the user that every plain button carries the same
risk, which is false.

`ThemeManager.cs:149-150` wires `Theme.Danger` / `Theme.DangerText` (contrast-checked
in `ThemePalette.cs`); `Styles.xaml` never references either; the only consumers are
alerting tiles (`TileViewModel.cs:61-62`, `SettingsViewModel.cs:1590-1591`), and
every other mention in the tree is a comment explaining a decision *not* to use it.
Remove / Clear / Delete buttons in eleven windows render exactly like Undo, Cancel
and Browse…: `BulkRenameWindow.xaml:167,169` · `MergePdfsWindow.xaml:53,55` ·
`MatchMergeWindow.xaml:103,104` · `PageCountsWindow.xaml:41,42` ·
`ZipToolsWindow.xaml:60,62` · `UnlockWindow.xaml:210,212` · `FilenameListWindow.xaml:73`
· `SettingsWindow.xaml:429,850` · `ManageSavedWindow.xaml:61` · `LabelMakerWindow.xaml:48`.

**Fix:** a `DestructiveButton` style (Danger border and text on Surface) applied at
those sites. **Pin:** a theme test in the `PrimaryButtonLabel` lint's shape: every
button whose name or content starts with Remove / Clear / Delete / Reset uses it —
fails today at all eleven sites.

### UX-11 — no animation honours reduced motion, and the code says so [V]

*Aesthetic-Usability*, read the right way round: polish buys patience only from
users it does not hurt, and a user who has told Windows to stop moving things has
opted out.

`ReadyView.xaml:18-24` records "grepped for `SystemParameters.ClientAreaAnimation`
across src/OrdoSort.Wpf — zero hits"; it is still the only mention in the tree
(QC re-grepped for `ClientAreaAnimation`, `ReducedMotion`, `AnimationsEnabled`).
Sites: the tile cascade (`ReadyView.xaml:48-163`, eight `DataTrigger` blocks), the
notice-rail slide (`MainWindow.xaml:64-72`) and a second fade there (`:402-407`), and
the confirmation-card fade (`ProcessingView.xaml:169-180`) — 57 `Storyboard` /
`DoubleAnimation` lines in all. UI-19 asks for the cascade's eight blocks to become
one converter; do both in one change.

**Fix:** one `AnimationsEnabled` (reads `SystemParameters.ClientAreaAnimation`;
optionally an Appearance toggle) gating the four sites — a `DataTrigger` on a
static, or zero durations. **Pin:** with it off, the cascade's `BeginTime` is zero
(a forward pin).

### UX-12 — merge order is drop order with no way to change it (Merge PDFs) [V]

*Tesler* — page order is the one decision the tool cannot make for the user, and it
gives them no control for it.

`MergePdfsViewModel.cs:467-473` iterates `Rows` in order, and rows are appended on
drop (`ZipListViewModel.cs:405`); `MergePdfsWindow.xaml` has no move or reorder
control. Fixing an order means remove and re-add in sequence.

**Fix:** Move up / Move down on the selection — Settings' route list already has the
↑ / ↓ pair (`SettingsWindow.xaml:430-435`).

### UX-13 — validation only on OK, pooled into one dialog, while live validity is computed and discarded (Settings) [V]

*Parkinson* — inline validation so the user does not wait for a round-trip to learn
about line one.

`HardErrors()` (`SettingsViewModel.cs:2225-2316`) is the only check; `TryBuildResult`
(`:2363-2371`) shows every tab's problems in one `Warn` with no tab switch and no
focus. Meanwhile `RouteEditVm.ColorValid` (`:93`) and `WatchEditVm.ColorValid`
(`:336`) raise on every keystroke and are bound **nowhere** (zero matches in any
`.xaml`; the colour boxes at `SettingsWindow.xaml:752` and `:1212` carry only the
`Text` binding, and the swatch converter paints an invalid colour transparent, which
looks like "none chosen") — "reddish" in Button colour gets nothing until OK. QC-17
(the unchecked suffix colon) is the adjacent, different gap.

**Fix:** bind `ColorValid` to the two colour boxes (the folder fields' `Problem` /
`NoteText` pattern sits beside them); on OK failure select the tab and focus the
first offender.

### UX-14 — path fields reject Explorer's "Copy as path" (Settings) [V]

*Postel*.

Every path assignment is `.Trim()` only — `SettingsViewModel.cs:2435-2446`, `:183-184`,
`:361-363` — and there is no quote stripping anywhere in Wpf or Core (the only
`"`-handling hit is `Csv.cs:92`, which *adds* quotes). Shift-right-click → Copy as
path wraps the result in quotes; pasted, the box looks right and the probe says the
folder does not exist, with no hint why — `PathIdentity.cs:47` cannot even canonicalise
it, since `"` is illegal in a Windows path.

**Fix:** strip one matching pair of quotes in the shared normaliser those
assignments already pass through. **Pin:** a quoted `S:\in\` normalises to the bare
path — fails today.

### UX-16 — Zip is the primary while Extract is plain, in a window named for both [V]

### UX-17 — Filename list and PDF page counts have no primary action [V]

*Peak-End* — error recovery is a designed moment, and a raw `IOException` message

(`IOException` / `UnauthorizedAccessException` / `Exception`) straight into the
status line or a dialog: `StandardiseNamesViewModel.cs:186,194,339` ·
`BulkRenameViewModel.cs:169-170,333` · `HistoryViewModel.cs:153` ·
`LabelMakerViewModel.cs:530` · `PageCountsViewModel.cs:271` ·
`FilenameListViewModel.cs:664` · `PrintPreviewWindow.xaml.cs:137` ·
`MatchMerge.cs:434`. Exporting History while the CSV is open in Excel therefore shows
"The process cannot access the file … because it is being used by another process",

cause-specific advice for the common types (sharing violation → "close it in the

used at those sites, with the technical text going to `crash.log` as

### UX-34 — Done keeps the split layout and blanks the viewer, so the session's end shows a large empty pane [V][U]

*Peak-End* — the confirmation screen is the one users remember, and this one is
two-thirds empty.

`ShowDone` (`ShellViewModel.cs:1370-1373`) sets `Screen.Done` and calls

(`WebViewPdfViewer.cs:200-205`). `ApplyWindowMode` (`MainWindow.xaml.cs:215-219`)

stays: `ViewerCol` `Width="*" MinWidth="320"` (`MainWindow.xaml:379`) beside the
430 px panel that carries the summary. Nothing sets the WebView2
`DefaultBackgroundColor`, so `about:blank` paints the control's default white — in
the four dark schemes, a white rectangle beside the dark Done card.

**[U] measure:** end a session in a dark scheme and look at the pane. **Fix:**
compact on Done as on Ready (`IsDone` already exists, `ShellViewModel.cs:392`), or
keep the last filed document's preview in the pane; either way set a themed
`DefaultBackgroundColor` so a blank pane is never white on dark.
